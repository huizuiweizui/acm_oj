# 考试 / 作业平台设计（M1–M4）

> 把竞赛 OJ 扩展为面向全校的考试/作业平台。参照拼题 A（PTA）的「题目集」模型。涉及 `Question`、进化后的 `Assignment` 等模型，以及 `question_api_views.py` / `exam_api_views.py`。

---

## 1. 设计目标

从「竞赛 OJ」到「全校考试平台」，差距在三件事（纯 OJ 都没有）：

1. **多种题型**——期末机考一半是选择/判断/填空，不只是编程题。
2. **考试模式**——限时、防作弊审计、考试中不泄题/不泄排名。
3. **成绩管理**——分值、部分分、成绩单、导出。

核心抽象：一个统一容器「题目集」，有**练习 / 作业 / 考试**三态，可同时装编程题与客观题。

## 2. 数据模型全景

```
Question                客观题题库（单/多选·判断·填空），独立于编程题 Problem
Problem (+扩展)          加 problem_type / function_templates 支持函数题
Submission (+扩展)       加 assignment（考试归属）/ raw_code（函数题原始函数）

Assignment (进化)        题目集容器：category 三态 + 考试配置字段
├── AssignmentProblem    编程题条目（+score 分值）
└── AssignmentQuestion   客观题条目（+score 分值）

ExamParticipation        学生的一次考试会话（计时 / 切屏 / 状态）
QuestionAnswer           学生对某客观题的作答 + 自动判分结果
```

迁移：`0016`（Question）、`0017`（容器+答题）、`0018`（函数题）。

## 3. M1 客观题题库

### 模型与判分

`Question` 用 JSON 字段灵活承载四种题型的选项与答案：

| 题型 | options | answer |
|------|---------|--------|
| 单选 single | `[{key,text}]` | `["A"]` |
| 多选 multiple | `[{key,text}]` | `["A","C"]` |
| 判断 judge | — | `["T"]` / `["F"]` |
| 填空 fill | — | `[["答案1","可接受写法"],["第二空"]]` |

`check_answer(submitted)` 自动判分：

- 单/多/判断 → 集合相等（多选顺序无关）
- 填空 → 逐空比对，每空可配多个可接受写法（任一命中即对），可选忽略大小写/首尾空格

### API 与校验

教师/管理员 CRUD（`question_api_views.py`）。**校验在视图层做全量校验**（单选答案须 1 项、选项 key 不重复、答案须是选项之一……）；PATCH 时先合并旧值与新值再整体校验，避免局部更新破坏题型自洽。

## 4. M2 函数题（PTA 式，复用评测核心）

学生只填**函数体**，系统拼接隐藏驱动后走现有评测——典型的「不碰评测核心」。

| 字段 | 作用 |
|------|------|
| `Problem.problem_type` | `standard` / `function` |
| `Problem.function_templates` | `{语言:{template 给学生的签名, prefix 隐藏前缀, suffix 隐藏 main 驱动}}` |
| `Problem.wrap_code(lang, code)` | 拼成 `prefix + 学生函数 + suffix` 完整程序 |
| `Submission.raw_code` | 学生原始函数（函数题）；标准题为空 |

**双存设计（关键）**：评测器读 `submission.code`，故必须存完整程序；但完整程序含公共驱动，查重会被样板污染，所以学生原始函数单存 `raw_code`，**查重只比 `raw_code`**。

详情序列化**只下发 template，绝不下发 prefix/suffix**（否则学生看到判题驱动）。

## 5. M3 考试容器 + 答题流

### 容器进化

把现有 `Assignment` 进化为三态容器（而非另造），复用团队作业逻辑、风险最低：

- `category`：`practice` / `homework` / `exam`
- 考试专用：`start_time` / `end_time` / `duration_minutes`（个人限时）/ `shuffle`（打乱）/ `track_focus`（记切屏）/ `hide_rank`（隐藏排名）

### 学生答题流（5 端点）

```
POST /assignments/<aid>/enter/        进入，建会话开始计时（考试校验时间窗口）
GET  /assignments/<aid>/paper/        拉试卷（剥标准答案，稳定打乱）
POST /assignments/<aid>/answer/       提交单题，自动判分
POST /assignments/<aid>/submit/       交卷，结算总分
POST /assignments/<aid>/focus-loss/   切屏上报
```

### 四个关键设计

| 设计 | 做法 |
|------|------|
| **不泄题/不泄对错** | 试卷端客观题只含 `content/options/my_answer`，无 `answer`/`correct`；考试中作答只回 `{saved:true}`，交卷后才揭晓 |
| **稳定打乱** | `shuffle` 时按 `md5(user_id + item_id)` 排序——同一学生每次刷新一致、不同学生不同 |
| **限时** | 个人截止 = `min(窗口结束, 进入 + 个人限时)`；前端用服务器时间做客户端时钟校准，到点自动交卷 |
| **防作弊=行为审计** | 切屏靠 `visibilitychange`/`blur` 上报。**前端可绕过，论文要如实写成审计而非强保证** |

## 6. M4 成绩管理

### 测试点部分分

编程题得分 = `round(分值 × 最佳提交的测试点通过率)`。通过率复用评测器写入的 `Submission.test_results`（`[{idx,status,time_ms}]`），取该生对该题所有提交里 AC 测试点占比的最大值。这让编程题不再「AC 满分 / 否则 0」，而是按完成度给分。

### 批量成绩单（性能要点）

`/assignments/<aid>/gradebook/` **固定 3 次查询、与班级规模无关**：

```
查询1：团队成员           → 一次
查询2：客观题得分聚合     → 一次（按 user 分组）
查询3：编程题提交         → 一次
        ↓ Python 内合并计算每人总分
```

避免了「每人一查」的 N+1。配套 Excel 导出（复用 openpyxl）与单生作答详情 `/students/<uid>/result/`。

## 7. 前端（M13 的考试部分）

沿用既有设计系统（`<script setup>` + scoped CSS + CSS 变量，无第三方 UI 库），4 个界面：

| 页面 | 难点 |
|------|------|
| `QuestionBankView` 题库管理 | **类型感知出题表单**：四种题型各自的答案编辑器；选项用下标管理、key 自动 A/B/C（删选项不错位） |
| `TeamDetailView` 组卷（扩展） | 三态 + 考试配置 + 编程/客观题各带分值 + 实时满分合计，向后兼容旧 `problem_ids` |
| `ExamView` 学生答题 | 倒计时（时钟校准）+ 客观题自动保存 + 切屏监测 + 交卷结算 + 考试中不揭晓 |
| `GradebookView` 成绩单 | 全班得分表 + Excel 导出 + 单生详情；入口连到查重页 |
