> 这块不是某个功能，而是"整个系统怎么搭、怎么保证质量"。评委常问系统设计和测试，必备。配套技术文档：`docs/06-工程架构与测试方法.md`。

## 一、答辩讲稿（口播，约 2–3 分钟）

> "最后讲一下整体的工程架构和我怎么保证质量。
>
> **架构是分层的。** 前端是 Vue 单页应用，通过 REST API 和后端通信，用 JWT 认证。后端我刻意做了**分层**：接口层只负责权限、序列化和流程编排；真正的**算法和业务逻辑下沉到一个独立的服务层**。比如查重、Rating 这些算法都是**纯 Python 模块、不依赖 Web 框架**，这样它们可以单独测试、单独跑实验——这对我做论文实验很重要。
>
> **扩展时我守了两条原则。** 一是**'按功能分模块'**：每个新功能（查重、考试、题单、题解……）都是一个独立的接口文件，互不缠绕，好维护好测试。二是**'加表不改表'**：扩展时只新增表或给现有表加可空字段，不动旧逻辑，所以原来的竞赛功能一点没退化。一共 9 个数据库迁移，全是增量的。
>
> **测试上我用了一个特别的方法。** 因为我用的是真实的 MySQL 数据库、没有独立测试库，我用'**事务包裹 + 末尾回滚**'的方式做端到端测试——在一个数据库事务里造测试数据、用框架真实地调用接口、断言返回结果，最后**抛异常回滚**，所以跑完测试数据库一点没被污染。纯算法模块甚至不依赖框架，直接加载文件就能测。**每个功能模块我都写了这样的测试并跑通**，比如查重的区分度、Rating 的单调性和守恒性、考试流程不泄答案，都是这么验证的。
>
> **我也如实说明：** 目前完成的是后端逻辑测试和前端构建验证，**还没有做大规模浏览器实跑和并发压测**，这些我在论文的'未来工作'里写清楚了。"

## 二、原理拆解

- **为什么分层**：算法和 Web 解耦后，算法可独立测试/复现实验；界面/接口变化不影响算法。
- **为什么按功能分模块文件**：单一职责，降低耦合，避免一个巨型文件难维护、易冲突。
- **"加表不改表"为什么安全**：旧数据零迁移成本、旧逻辑零改动，扩展不破坏既有功能。
- **回滚式测试为什么干净**：数据库事务的原子性——要么全提交、要么全回滚。末尾故意回滚，等于"演了一遍但不留痕"。

## 📚 这里你需要懂的

- **分层架构**：表现层（前端）/ 接口层（API）/ 服务层（算法）/ 数据层（数据库）各干什么。

- **数据库迁移（migration）是什么**：模型改了怎么同步到数据库表。
- **数据库事务 / 原子性**：为什么"事务 + 回滚"能做到测完不留痕。
- **N+1 查询、批量查询**（成绩单优化也用到）。
- **你的测试覆盖了什么**（能举 2-3 个例子）。

## 五、评委可能这样问 + 怎么答

**Q：你怎么保证这些功能是对的？做测试了吗？**
> A：做了。每个功能模块我都写了端到端测试——用框架真实调用接口、断言返回。比如查重我验证了抄袭样本和原创样本的区分度约 2 倍、Rating 验证了名次单调和近似零和、考试验证了试卷不含标准答案。纯算法模块还能脱离框架单独测。

**Q：你没有用测试数据库？那测试会不会弄脏数据？**
> A：不会。我用数据库事务包住整个测试，造数据、调接口、断言都在事务里，最后故意抛异常回滚，利用事务的原子性保证"演一遍但不留痕"。所以即便在真实库上测也不污染。

**Q：为什么把算法单独抽成模块？**
> A：两个原因：一是解耦，算法不依赖 Web 框架，接口变化不影响它；二是**可复现实验**——查重、Rating 这些是我论文的实验对象，抽成纯 Python 模块后我能直接喂数据跑、出实验结果，这对写论文很关键。

**Q：这么多功能，你怎么保证没把老功能改坏？**
> A：靠"加表不改表"原则——扩展只新增表或加可空字段，不动现有模型和逻辑，9 个迁移全是增量。所以原有的题库、评测、比赛功能不受影响。

**Q：（被问工作量）你一个人做了多少？**
> A：13 个功能里程碑，后端 6 个新接口模块、9 个数据库迁移、3 个有算法深度的核心模块，前端十几个页面，每个模块配端到端测试，并写了完整的实现文档和这套答辩材料。
