# 答辩讲稿 08 · 后端架构与评测流水线

> 这块讲"后端在运行时到底怎么转"——尤其是 OJ 最硬的两件事:**怎么安全地跑学生写的不可信代码**、**全校同时交卷怎么不崩**。评委问系统设计、安全、并发,答案都在这。配套技术文档:`docs/07-后端架构与评测流水线.md`;部署见 `plan/生产部署方案.md`。
>
> 与 07(工程架构与测试)的分工:07 讲"代码怎么组织、怎么测";本篇讲"评测引擎怎么实现、怎么扛并发"。

## 一、答辩讲稿(口播,约 2–3 分钟)

> "再讲一下后端最核心的部分——评测引擎,以及它怎么面向全校稳定运行。
>
> **先说整体。** 后端是 Django 的 REST API,分层很清楚:Nginx 负责入口和 HTTPS,Gunicorn 跑 Django,请求进来先用 JWT 认出用户、再过权限校验、最后视图编排业务。这部分是常规的。
>
> **真正难的是评测。** 因为我要运行的是**学生写的、不可信的代码**——它可能死循环、可能开爆内存、甚至可能想读服务器文件或者联网攻击。所以每一次提交,我都把代码放进一个**一次性的 Docker 容器**里编译运行:容器**断网**、**内存和 CPU 都设了硬上限**、**限制了进程数**防止 fork 炸弹、源码是**只读挂载**、跑完**立即销毁**。这样学生代码被关在牢笼里,出不来。判定结果也来自这个过程:超时就是 TLE,内存超限被系统杀掉、退出码 137 就是 MLE,逐个测试点比对输出得出 AC 还是 WA。
>
> **第二个难点是并发。** 这是我这次专门改造的地方。原来我的做法是:一提交就**起一个线程**去评测。这个写法面向全校有致命问题——全班一百个人同一分钟交卷,就会瞬间起一百个线程、一百个 Docker 容器,直接把服务器打爆;而且服务一重启,正在评测的线程就全丢了。
>
> 所以我把它改成了**任务队列**:用 Celery 加 Redis。提交后,后端只是把评测**任务丢进队列就立刻返回**,前端拿到一个'排队中'的状态,每两秒轮询一次结果;真正的评测由**独立的 Worker 进程**去消费队列。这样带来三个好处:第一,**Worker 的并发数就是同时最多几个评测的硬闸门**,考试洪峰时大家排队、但机器不崩;第二,**服务重启不丢任务**,因为任务存在 Redis 里;第三,以后压力大了,我可以**单独加一台评测机**,只要把它的 Redis 地址指过来就行,Web 完全不用动。
>
> **除了评测,我还做了一轮生产加固:** 把'自定义运行'这种同样会执行代码的接口也改走队列(它原来在请求线程里直接跑、会绕过并发闸门);加了接口限流防刷、统一日志和健康检查;还用定时任务自动回收卡死的评测、清理临时文件。
>
> **我也如实说明局限:** **功能我已经端到端测过了**——完整评测流程、卡死自愈、限流都验证没问题;**真实 Redis + 独立 worker 的分布式路径**用 Docker 起 Redis 实跑验证过;连**生产用的 Docker 沙箱隔离**也 build 了镜像实跑验证(网络、内存限制都确实生效)。**真正只剩一件**:全校规模的并发压测,要在 Linux 服务器上模拟几百人同时交卷才有意义,我写进了未来工作。"

## 二、原理拆解(自己要更明白一层)

- **沙箱为什么能隔离**:Docker 容器是操作系统级隔离(独立的进程/网络/文件视图)。`--network=none` 断网、`--memory` 触发 OOM-kill、`--pids-limit` 防 fork 炸弹、只读挂载防篡改——每个参数对应堵一类攻击。
- **为什么线程扛不住而队列可以**:线程在 Web 进程里、没有全局上限,来多少起多少;队列把"接收"和"执行"解耦,执行端的 Worker 并发数是固定的闸门,多出来的任务排队而不是挤爆机器。
- **为什么用轮询不用长连接**:评测结果写进数据库,前端隔两秒读一次即可。实现简单、无状态、对反向代理友好;代价是最多两秒延迟,对 OJ 完全能接受。
- **为什么评测任务不自动重试**:评测成功会累加 AC 计数、结算 Rating,如果失败自动重跑会**重复计数**。所以我让它不重试,出异常就兜底标记为运行错误,宁可让学生重交,也不污染数据。
- **开发态为什么不用装 Redis**:我让任务队列在开发模式(DEBUG=True)下默认"同步执行"——本地直接跑、零依赖;生产模式自动切换成真实队列。一套代码两种行为。
- **卡死怎么自愈**:worker 万一崩了会留下卡在 Judging 的提交,定时任务每 5 分钟把超时的自动置为错误,学生可重交,不会永远卡住。

## 📚 这里你需要懂的(答辩前务必弄明白)

- **一次评测的完整链路**:提交 → 落库排队 → Worker 取任务 → 沙箱编译运行逐测试点 → 比对输出得判定 → 写回结果 → 前端轮询看到。
- **七种判定怎么来的**:AC/WA(比对输出)、TLE(超时)、MLE(退出码 137)、RE(非零退出)、CE(编译失败)、NT(无测试点不计分)。
- **Docker 沙箱的几个安全参数分别防什么**(至少能说出断网、内存上限、进程数限制、只读挂载)。
- **线程方案的四个问题**(无并发上限 / 重启丢任务 / 多进程失控 / 不能分机扩容)和队列怎么解决。
- **"并发数 = 评测上限"这个闸门**:这是你回答"会不会崩"的核心。
- **JWT 无状态认证**:为什么无状态利于水平扩容。

## 🎓 需要补学的知识(不熟就去补)

- **容器与隔离**:Docker 是什么、容器 vs 虚拟机、为什么能隔离不可信进程(重点)。
- **消息队列 / 任务队列**:生产者-消费者模型、Celery + Redis 的角色(broker 是什么)。
- **进程 vs 线程**:为什么 CPU 密集 + 隔离需求下,独立进程比线程合适。
- **WSGI / Gunicorn**:Django 生产为什么不用自带 runserver。
- **轮询 vs WebSocket vs SSE**:三种"服务器→前端"更新方式的取舍(你评测用轮询、AI 问答用 SSE)。
- **(了解)负载/压力测试**:能说出"上线前要模拟并发交卷压测"即可。

## 五、评委可能这样问 + 怎么答

**Q:学生提交的代码是任意代码,你怎么防止它搞破坏、攻击你的服务器?**
> A:每次提交都在一次性的 Docker 容器里跑,容器断网、内存和 CPU 有硬上限、限制进程数防 fork 炸弹、源码只读挂载、跑完即销毁。学生代码被隔离在容器里,既联不了网也动不了宿主机文件。开发时我有个直接运行的模式方便调试,但它没有隔离,我在文档里明确标注**生产必须开 Docker 沙箱**。

**Q:全校几千人,要是一次大考大家同时交卷,系统会不会崩?**
> A:不会被冲垮,这正是我做异步队列的目的。提交只是把任务丢进 Redis 队列就立即返回,真正评测由独立 Worker 消费,**Worker 的并发数就是同时最多几个评测的硬上限**。洪峰时多出来的提交在队列里排队,学生看到"排队中"稍等一会,但机器负载是受控的、不会被打爆。要更快出分就再加一台评测机指向同一个队列。

**Q:为什么用消息队列?直接开线程或者多开几个进程不行吗?**
> A:线程方案有四个问题:没有并发上限(来多少起多少,洪峰会爆)、服务重启正在跑的评测会丢、多个 Web 进程各起各的线程没法全局控制、而且评测和 Web 绑死没法单独扩容。队列把接收和执行解耦,执行端并发固定可控、任务持久化不怕重启、还能独立加评测机——四个问题一次解决。

**Q:TLE 和 MLE 是怎么判出来的?**
> A:超时是给容器设了执行时限,超过就判 TLE;内存是用 Docker 的内存硬上限,超限的进程会被系统 OOM 杀掉、退出码是 137,我据此判 MLE。时间和内存的隔离都靠沙箱,不靠在代码里估算。

**Q:为什么前端用轮询拿结果,不用 WebSocket 实时推送?**
> A:评测结果会写进数据库,前端每两秒读一次就够了。轮询实现简单、服务端无状态、对反向代理特别友好;WebSocket 要维护长连接、复杂度高,而 OJ 对两秒延迟完全不敏感,所以我选了更简单可靠的方案。AI 问答那种需要逐字输出的场景我才用了 SSE 流式。

**Q:评测过程中如果 Worker 挂了或者出异常,会不会算错分、或者重复加分?**
> A:不会重复加分——我特意让评测任务**不自动重试**,因为评测成功会累加 AC 数和 Rating,重试会双计。出异常时我兜底把这条提交标记成运行错误,数据保持一致,学生重交即可。任务本身存在 Redis 里,Worker 重启不会丢队列里还没处理的任务。另外我加了个定时任务,每 5 分钟扫一遍卡在评测中超过 15 分钟的提交(worker 崩溃的兜底)自动标记错误,保证不会有提交永远卡住。

**Q:会不会有人写脚本疯狂刷提交接口把系统拖垮?**
> A:我给提交和自定义运行加了接口限流(按用户每分钟上限),超了会被挡下;真正的执行又有 Worker 并发闸门兜底。两层一起,刷接口既刷不动、也压不垮评测。

**Q:(诚实牌)这套架构有没有还没做完的地方?**
> A:**功能层面我端到端测过了**:先用 eager 同步模式 + 回滚式测试(十几项全过,含真实 g++ 编译运行的完整评测流水线重判仍 AC、卡死自愈、限流),再用 **Docker 起真实 Redis + 独立 worker 实跑分布式路径**(5 项全过、worker 日志确认逐个消费)。所以逻辑和真实队列都验证过了。生产的 Docker 沙箱隔离我也 build 镜像实跑验证过(C++/Python 容器内评测、网络隔离、内存上限都确实生效)。**真正只剩一件**:全校规模并发压测,得在 Linux 服务器上模拟几百并发——这是上线前最后一关。(之前发现的几处会绕过队列的同步执行接口已全部改走队列。)
