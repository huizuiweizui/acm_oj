# 后端架构与评测流水线

> 讲清楚后端在**运行时**到底怎么转：一个请求 / 一次代码提交，从进来到出去经过了哪些环节；评测为什么要做成异步、沙箱怎么把学生代码关起来。论文「系统设计 / 系统实现」章节可取材。
>
> 与 06 的分工：06 讲**代码怎么组织、怎么测试**；本文讲**后端运行时与评测引擎怎么实现**。部署上线见 `plan/生产部署方案.md`。

## 1. 后端分层与请求生命周期

平台是**前后端分离**：Vue 3 SPA 通过 `/api/*` 调 Django REST API，后端不渲染页面、只出 JSON。

```
浏览器 ──HTTPS──▶ Nginx ──▶ Gunicorn ──▶ Django REST Framework
                                              │
            ┌─────────────────────────────────┼─────────────────────────────┐
            ▼                 ▼                ▼               ▼
      JWT 认证          权限类(Permission)   视图(View)      序列化器(Serializer)
   identify user    IsTeacherOrAdmin...   编排业务        Model ⇄ JSON
                                              │
                                              ▼
                              judge/services/（算法/服务层，不耦合请求）
                                              │
                                              ▼
                                       judge/models.py ⇄ MySQL
```

**一个请求的标准链路**：
1. Nginx 终止 HTTPS，静态走本地、`/api/` 反代给 Gunicorn；
2. DRF 先用 **SimpleJWT** 解 `Authorization: Bearer <token>` 认出用户；
3. **权限类**校验（角色 / 团队归属）；
4. **视图**做业务编排（查询、写库、调服务层）；
5. **序列化器**把模型对象转成 JSON 返回。

> 分层铁律（沿用 06）：**视图只做「权限 + 序列化 + 编排」，算法/业务下沉到 `services/`**。所以 `judger.py`、`similarity.py`、`rating.py` 都是不依赖 HTTP 请求的纯模块，能独立单测、能复现实验。

### 技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| Web 服务器 | Nginx + Gunicorn(gthread) | 反代 + WSGI；SSE 需线程型 worker |
| 框架 | Django 4.2 + DRF | REST API |
| 认证 | djangorestframework-simplejwt | 无状态 JWT |
| 任务队列 | **Celery + Redis** | 评测 / AI 反馈异步化（本文 §5） |
| 数据库 | MySQL 8 | |
| 执行隔离 | Docker 沙箱 | 每次提交一个容器（本文 §4） |
| AI / 向量 | LLM API + 向量检索 | AI 反馈 + RAG 问答（本文 §6） |

## 2. 认证与权限

- **认证**：登录签发 JWT（access 8h / refresh 14d，见 `SIMPLE_JWT`）。前端 axios 拦截器自动带 `Bearer`，服务端无 session、可水平扩容。
- **权限**：DRF `BasePermission` 类，角色为**包含式** admin ⊇ teacher ⊇ student：
  - `IsTeacherOrAdmin`：`profile.role in ('teacher','admin')`
  - `IsAdminOnly`：仅 admin
- **水平越权防护**：光有角色不够，团队类接口还要校验「当前用户与该 team 的归属」。`team_api_views.py` 用 `_is_creator_or_admin(user, team)` 等小工具，并下发 `can_manage` 给前端控制按钮渲染——但**后端每个接口都独立校验**，前端隐藏入口不作数。这样教师 A 改 URL 也看不到教师 B 的班级。

## 3. 评测流水线（核心）

这是 OJ 的心脏，也是「全校用」最吃资源的环节。

### 3.1 端到端时序

```
学生点提交
   │  POST /api/problems/<id>/submit/
   ▼
SubmitCodeAPIView：校验语言/代码长度 → 函数题包裹隐藏驱动 → 识别比赛/作业归属
   │  Submission(status=Pending) 落库 + submit_count+1
   │  judge_submission_task.delay(submission.id)        ← 入队，立即返回
   ▼
（HTTP 立即响应 {submission_id, status:"Pending"}）

—— 以下在 Celery Worker 进程，与请求线程解耦 ——
judge_submission_task：status=Judging → 调 judge_submission(sub, problem)
   │
   ├─ 无测试点         → NT（不计分，等管理员补数据）
   ├─ 编译失败         → CE（错误信息截断 2000 字）
   └─ 逐测试点运行：
        for tc in test_cases:
            run_code（沙箱）→ 比对输出
            timed_out → TLE | returncode==137 → MLE | !=0 → RE | 输出不一致 → WA | 一致 → AC
        汇总 overall_status + 每点结果 test_results=[{idx,status,time_ms}]
   │
   ├─ 首次 AC：Problem.ac_count+1、UserProfile.ac_count+1、更新 Rating
   ├─ 比赛提交：更新 ICPC 罚时/分数
   └─ ai_feedback_task.delay()                          ← AI 反馈再入队
   ▼
前端每 2s 轮询 GET /api/submissions/<id>/，状态非 Pending/Judging 即停
```

### 3.2 判定细节

- **时间**：题目 `time_limit` 单位 ms（运行时换算成秒），沙箱另加启动缓冲再判 TLE；只在全 AC 时记录最大耗时。
- **内存**：Docker `--memory` 硬限，超限被 OOM-kill，退出码 **137** 即判 MLE。
- **输出比对**：`_normalize()` 统一换行、去行尾空白后逐行比较（容忍尾随空白，不容忍内容差异）。
- **状态机**：`Pending → Judging → {AC, WA, TLE, MLE, RE, CE, NT}`。
- **NT（无测试点）**：不计 AC、不计 Rating、不算「尝试」，等补测试数据后重测——避免脏数据污染统计。

### 3.3 轮询模型（而非长连接）

前端「提交→轮询」是刻意选择：实现简单、无状态、对反代友好，代价是最多 2s 延迟，对 OJ 完全可接受。评测结果写回 MySQL，轮询只读库，与 Worker 完全解耦。

## 4. 沙箱隔离（安全核心）

学生代码是**不可信输入**，必须关进牢笼。沙箱有两套后端（`judge/services/sandbox.py`）：

| 后端 | 触发 | 隔离 | 用途 |
|------|------|------|------|
| 直接子进程 `_direct_run` | `USE_DOCKER_SANDBOX=False` | **无** | 仅 Windows 本地开发 |
| Docker 容器 `_docker_run` | `USE_DOCKER_SANDBOX=True` | 强 | **生产必须** |

### Docker 安全参数（每个都在防一类攻击）

| 参数 | 防什么 |
|------|--------|
| `--network=none` | 断网，禁止外联 / 偷数据 / 打内网 |
| `--memory` / `--memory-swap` | 内存硬上限，超限 OOM-kill（→ MLE） |
| `--cpus=1` | 单核，防占满 CPU |
| `--pids-limit=64` | 限进程数，防 fork 炸弹 |
| `-v tmp_dir:/sandbox:ro` | 源码/二进制**只读**挂载，运行期不能改 |
| `--tmpfs /tmp:exec,size=128m` | 容器内可写临时区（给 JVM/Python），不落宿主机 |
| `--rm` | 跑完即焚，不留痕 |

> **为什么生产必须开 Docker**：直接子进程模式下，学生代码以服务进程的身份运行，能读写服务器文件、联网——面向全校开放时这是致命漏洞。`sandbox.py` 顶部注释已显式标注 direct 模式「NO isolation」。

## 5. 异步任务架构（Celery + Redis）★ 本次改造

### 5.1 为什么不能用线程（改造前的问题）

改造前，提交后用 `threading.Thread` 在 Django 进程里直接起评测线程。面向全校时这套扛不住：

1. **无并发上限**：全班 100 人同分钟交卷 → 100 个线程 → 100 个 Docker 容器同时起 → CPU/内存爆掉。
2. **重启即丢**：发版/重启 Gunicorn，在途评测线程全没，提交永远卡 Judging。
3. **多 worker 失控**：生产多个 Gunicorn worker 各起各的线程，没有全局节流。
4. **不可分机扩容**：评测和 Web 绑死在一个进程，无法单独加评测机。

### 5.2 改造后的设计

把「起线程」换成「丢队列，独立 Worker 消费」：

```
Django（生产者）── judge_submission_task.delay(id) ──▶ Redis 队列
                                                          │
                                  Celery Worker（消费者，并发 = N）──▶ docker run
```

- **入口**（`api_views.SubmitCodeAPIView`）：`judge_submission_task.delay(submission.id)` 一行替代整段线程代码。
- **任务**（`judge/tasks.py`，`@shared_task`）：
  - `judge_submission_task(submission_id)`：置 Judging → 调同步评测引擎 → 异常兜底置 RE。
  - `ai_feedback_task(submission_id, problem_id)`：评测后异步生成 AI 反馈，失败静默。
- **Celery app**：`acm_oj/celery.py` 定义、`acm_oj/__init__.py` 启动时加载、`config_from_object(namespace='CELERY')` 让所有 `CELERY_*` 设置生效、`autodiscover_tasks()` 自动发现 `judge/tasks.py`。

### 5.3 收益

| 维度 | 改造前（线程） | 改造后（Celery） |
|------|----------------|------------------|
| 并发上限 | 无 | `CELERY_WORKER_CONCURRENCY` = 同时最多几个评测 |
| 重启 | 在途任务丢失 | 任务在 Redis，重启不丢 |
| 扩容 | 不能 | 加一台评测机、`REDIS_URL` 指向主机即可 |
| Web 阻塞 | 抢 Web 进程资源 | 完全解耦，Web 只入队 |

> **关键旋钮**：`CELERY_WORKER_CONCURRENCY`（默认 4）就是「考试洪峰时同时最多几个 Docker 评测」的硬闸门，按评测机 CPU 核数设。这正是 06 文档列为最高风险的「评测沙箱并发」的答案。

### 5.4 两个工程取舍

- **开发零摩擦**：`CELERY_TASK_ALWAYS_EAGER` 默认跟随 `DEBUG`——`DEBUG=True` 时任务**同步执行**，开发机不用装 Redis/起 Worker，行为同改造前；`DEBUG=False`（生产）自动走真实队列。要本地验证真实链路：装 Redis + `celery -A acm_oj worker -l info --pool=solo`（Windows prefork 不可用，故 `--pool=solo`；Linux 用默认 prefork）。
- **评测不自动重试**：评测会用 `F()` 表达式累加 AC 计数并结算 Rating，重复执行会**双计**。故 `judge_submission_task` 不设重试，异常时只兜底置 RE。AI 反馈任务失败则直接静默（无副作用，丢了无所谓）。
- **防循环引用**：`tasks.py` 与 `_async_ai_feedback` 的重依赖都在函数体内**延迟导入**，保证 Worker 启动时 `autodiscover` 导入 `tasks.py` 不触发 `tasks → judger → ai_feedback → tasks` 的环。

## 6. AI 反馈与 RAG

两处都复用同一套 LLM 调用，且都已异步化 / 流式化：

- **AI 评测反馈**：评测结束后 `ai_feedback_task` 调 `_ai_call()` 让模型点评代码（思路 + 改进），写入 `Submission.ai_feedback`。`LLM_API_KEY` 留空则自动禁用、返回空串，不影响评测。
- **算法 RAG 问答**（`services/rag.py` + `AskAIAPIView`）：把 `algorithm/` 笔记切块、向量化存库；提问时 `retrieve()` 做余弦相似度取 top-k 片段，拼进 prompt，`stream_answer()` 经 **SSE**（`StreamingHttpResponse` + `text/event-stream`）逐字推给前端。代码已设 `X-Accel-Buffering: no`，Nginx 侧需同步关缓冲（见部署文档）。

## 7. 关键设计决策小结

| 决策 | 选择 | 理由 |
|------|------|------|
| 前后端 | 分离，后端只出 JSON | SPA 体验 + 接口可复用 |
| 认证 | 无状态 JWT | 可水平扩容、对反代友好 |
| 评测触发 | **Celery 异步队列** | 并发可控、重启不丢、可分机扩容 |
| 执行隔离 | Docker 沙箱 per submission | 不可信代码强隔离 |
| 评测结果获取 | 前端轮询 | 简单、无状态、延迟可接受 |
| AI 流式 | SSE（非 WebSocket） | 单向推送，简单可靠 |
| 服务分层 | 算法下沉 `services/` | 可单测、可复现实验 |
