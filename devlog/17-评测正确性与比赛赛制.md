## 阶段十七：评测正确性与比赛赛制（P1）

接着阶段十六的审查清单往下做。这一轮集中在"比赛当天会出事"的那一类问题。

### Fix 1 — 每次提交泄漏一个临时目录

**问题**：`judge_submission()` 里 `tempfile.mkdtemp()` 之后没有任何 `rmtree`（对比自定义运行是清理了的）。每次评测在系统临时盘留一份源码 + 编译产物，一场几千次提交的比赛足够把评测机磁盘写满。

**修复**：把 `mkdtemp` 之后的整段包进 `try/finally`。必须用 `finally` 而不是在末尾加一行——这个函数有三类出口：CE 提前 `return`、正常跑完、沙箱抛异常。

**验证**（假沙箱驱动真实 `judge_submission`，逐条出口）：

```
正常评测(AC) / 答案错误(WA) / 编译失败(CE 提前 return)
超时(TLE) / 运行期抛异常          → 残留目录均为「无」
```

> 遗留：`settings.JUDGE_TEMP_DIR` 定义了但没有任何代码使用，评测临时文件实际落在系统临时目录。切换目录会影响 Docker 沙箱的 bind-mount 路径，需在 Linux 上一并验证，或干脆删掉这个配置项。

### Fix 2 — `/run/` 绕过了评测队列

**问题**：自定义运行在 web 请求线程里**同步**编译执行，`JUDGE_WORKERS` 完全管不到。阶段十五修的并发爆炸问题，在这个口子上原样存在——它同样编译、同样跑 10 秒。

**修复**：没有套用线程池，而是用信号量（`judge_queue.run_slot()`），原因有二：

1. 自定义运行是**同步接口**，请求线程必须原地拿到输出，把活挪进池子再阻塞等待反而多绕一圈
2. 更重要的是**只给排队等待设超时，不给执行设超时**。若用 `future.result(timeout=N)`，那个 N 得同时覆盖排队和执行，Java 那种编译慢的语言会被误判成"繁忙"

名额与评测**相互独立**（`JUDGE_RUN_WORKERS`，默认取 `JUDGE_WORKERS` 的一半），保证比赛时自定义运行抢不走判题 worker。拿不到名额等待超过 `JUDGE_RUN_QUEUE_WAIT`（默认 15s）即回 503 泄掉负载，而不是让请求挂着把 web 进程占满。

**验证**（名额调成 2、等待调成 1 秒便于观察）：

```
8 个并发请求 → 成功 4 个，被限流(503) 4 个，耗时 1.2s
实际最大同时执行数 = 2          ← 闸生效
压测结束后仍能立刻拿满 2 个名额   ← 名额已归还
代码块内抛异常后名额同样归还
```

### Fix 3 — IOI 赛制补齐测试点得分制

**问题**：`Contest.rule_type` 可选 IOI，建卷页面也能选，但 `update_contest_score()` 对非 ICPC 直接 `return`，排行榜也只有 ICPC 一套逻辑。结果是建了 IOI 赛，榜单按 ICPC 罚时排。

**计分规则**：每题满分 100，得分 = 通过测试点 / 总测试点 × 100（全过直接给满分，避免除不尽丢分）。新增 `Submission.score` 字段（migration `0015`）。**每条提交都算分**，不只是比赛提交——ICPC 赛制下也能展示"过了几成"。

**与 ICPC 的关键差别：取最高分，不是首次 AC**。ICPC 只需累加增量（首次 AC 加一分），但 IOI 下后交的提交可能更高分，**也可能更低**（选手改崩了），累加会算错。所以 `_update_ioi_score()` 直接用一条聚合查询按当前所有提交重算总分——既不漂移，重测和改判也天然正确。罚时恒为 0。

**榜单**：`_ioi_ranking()` 是独立分支，ICPC 逻辑一行没动。并列判定用"达成当前总分的时刻"（各题首次达到最高分的时间里最晚的一个），同分先到者靠前——IOI 官方其实没有这条，但榜单需要一个稳定顺序。

前端 `ContestRankingView.vue` 按 `rule_type` 切换：表头变成「总分 / 用时」，格子显示得分并按比例着色（满分绿 → 部分分橙黄 → 零分灰）。

**验证**（三人三题的 IOI 赛，事务回滚）：

```
alice A: 40分@10m → 100分@20m → 30分@30m(改崩)   B: 60分@40m
bob   A: 100分@15m                              B: 60分@25m
carol C: 100分@5m

总分  alice=160  bob=160  carol=100   ← 后交的 30 分没有拉低总分
名次  1 bob(25m)  2 alice(40m)  3 carol(5m)
alice 的 A 题记录首次达到 100 分的时刻(20m)，而非最后一次提交(30m)
```

> 未做：**每题固定 100 分**，没有题目权重。要支持"A 题 100 分、B 题 200 分"需给 `ContestProblem` 加满分字段并在建卷页开放填写。另外测试点没有独立分值字段，是按数量均分；要做 subtask 捆绑计分得先给测试点加分值和分组。

### Fix 4 — 比赛题目可见性

**问题**：原先是个死结——赛题设为 `is_published=True` 则赛前就能被翻出来刷，设为 `False` 则选手赛中也打不开。

**修复**：访问权不再只看 `is_published`，加一条"因参赛而获得"的通路。**赛题可以一直保持不公开**。

| | 未登录 | 路人 | 已报名选手 | 出题人/教师 |
|---|---|---|---|---|
| **题目清单** 赛前 | ✗ | ✗ | ✗ | ✓ |
| 赛中 | ✗ | ✗ | ✓ | ✓ |
| 赛后 | ✓ | ✓ | ✓ | ✓ |
| **未公开赛题的题面** 赛前 | ✗ | ✗ | ✗ | ✓ |
| 赛中 | ✗ | ✗ | ✓ | ✓ |
| 赛后 | ✗ | ✗ | ✗ | ✓ |

赛后题面仍锁着，由出题人决定何时公开。

写第一版时把出题人也挡在题面外了，结果是"能在比赛页看到题目清单、点进去却 404"，出题人连自己的题都没法预检——改成管理者始终放行。

`is_published` 的硬过滤原先散在四处（题面 / 提交 / 自定义运行 / 比赛详情），全部换成 `can_access_problem()`。题库列表保持只列 published，赛题不会混进普通题库被搜到。

前端：赛前列表为空时原本显示"暂无题目"，看着像这场没出题。改成说明原因，并且仍然告知题目数量（后端单独返回 `problem_count`，不下发标题）。

**验证**（DRF `APIRequestFactory` 打真实视图）：

```
题面   赛前: 未登录=404 路人=404 已报名=404 出题人=200
      赛中: 未登录=404 路人=404 已报名=200 出题人=200
提交   赛中: 未登录=401 路人=404 已报名=201 出题人=201
清单   赛前: 路人 隐藏(0题/共1)   赛中: 已报名 可见(1题/共1)
```

并断言赛前响应的 JSON 里不出现任何题目标题。

### Fix 5 — AI 反馈：裸线程 + 数据库连接泄漏

**问题**：`_async_ai_feedback()` 每条提交裸起一个 `threading.Thread`，和阶段十五修掉的是同一类问题。每个线程挂一次 30 秒的 LLM 请求、各自占一条数据库连接且从不归还——比赛时几百条提交同时评完，MySQL 的 `max_connections` 撑不了多久。

**修复**：改为固定大小线程池（`AI_FEEDBACK_WORKERS`，默认 2），并在每个任务首尾调 `close_old_connections()`。池里的线程是复用的，Django 不会像处理请求那样帮忙收连接，必须自己还。

另外：没配 LLM 时直接返回，不建池也不占线程；异常从 `except: pass` 改为记日志——静默失败的 AI 反馈很难查。

**验证**：

```
投递 30 个任务 → 实际工作线程 ['ai-feedback_0', 'ai-feedback_1']
线程数 = 2，并发峰值 = 2        ← 改之前是 30 个裸线程

连接归还对照实验（CONN_MAX_AGE = 0）：
  不清理（旧行为）                    线程结束时仍占用 = True
  调用 close_old_connections（新行为）  线程结束时仍占用 = False
```

> `sandbox.py` 里那三个线程不用管：它们是每个子进程的 stdin/stdout/stderr 泵，数量已被 `JUDGE_WORKERS` 间接卡住。

### Fix 6 — 私有赛密码

**问题**：`Contest.password` 字段建了从没用过，报名接口不做任何校验。**Fix 4 之后这个洞变严重了**——题目可见性现在挂在"是否报名"上，而报名完全不设防，等于私有赛的题谁都能看。

**修复**：公开赛照旧；私有赛必须给对密码（`secrets.compare_digest` 定长比较）；私有赛没设密码则只能由组织者添加；管理者不受限。前端在私有赛时多一个密码输入框，报名成功后重新拉一次详情（因为报名后才拿得到题目清单）。

**验证**：

```
公开赛    不带密码 → 201 报名成功
私有赛    不带密码 → 403 请输入比赛密码
         密码错误 → 403 比赛密码不正确
         密码正确 → 201 报名成功
私有无密码 路人 → 403 请联系组织者添加    出题人 → 201
未报名者看私有赛: problems_visible=False, problems=[]
```

> **比赛密码是明文存储的**（`CharField`，未改）。这是 OJ 的常见做法——组织者要能看到密码好分发给选手，哈希了就显示不出来。但它确实意味着拖库即泄露所有比赛密码。若要改成哈希，需加迁移并把建卷页调整为"重设密码"而非"查看密码"。
